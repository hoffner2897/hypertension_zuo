## 开发任务目标

BPHealth 当前目标是从本地 MVP 推进为完整的全栈产品：

- iOS 端支持登录、注册、会话刷新、资料设置、血压读数录入、历史记录、离线保存和后续同步。
- 后端使用 Node.js、Express、TypeScript、Prisma 和 PostgreSQL，承接认证、资料、血压读数、同步、图片识别和读数解读。
- iOS 端不保存 OpenAI API Key，血压计照片识别和 AI 辅助解读统一通过后端完成。
- 首版需要支持邮箱验证、短期 access token、长期 refresh token、账号删除、中英文本地化，以及非诊断性的健康趋势提示。
- 新增的「今日行动」方向用于探索基于血压状态、时间、场景和用户偏好的日常行动建议，但目前仍是 iOS 端 demo 阶段。

## 迁移到 Web Service / 网络服务的进度

### 已经具备迁移基础的部分

- 服务端已经不是单纯本地 mock，而是可部署的 Express + TypeScript API。
- 数据库模型已经使用 Prisma 管理，并有 PostgreSQL migration。
- `package.json` 已有生产启动脚本：`npm run start`。
- `package.json` 已有生产迁移脚本：`npm run db:deploy`。
- API 端点已经覆盖首版核心链路：
  - `/health`
  - `/auth/register`
  - `/auth/login`
  - `/auth/refresh`
  - `/auth/logout`
  - `/auth/me`
  - `/auth/verify-email`
  - `/auth/resend-verification`
  - `/auth/account`
  - `/profile`
  - `/readings`
  - `/readings/sync`
  - `/sync/readings`
  - `/readings/interpretation`
  - `/recognize-bp`
- iOS 端已经指向 staging API，因此客户端已经开始从本地开发地址切换到网络服务地址。

### 不能直接迁移或需要谨慎处理的部分

- 邮箱验证还没有真正强制启用：
  - 后端注册时目前直接设置 `emailVerifiedAt`。
  - `VerifyEmailView` 和验证接口存在，但 iOS root router 还没有把未验证用户挡在主流程之外。
- 生产环境不能使用开发默认 secret：
  - `ACCESS_TOKEN_SECRET` 必须替换为强随机值。
  - `.env` 不能提交，也不能使用本地开发数据库地址。
- 生产数据库迁移应使用 `npm run db:deploy`，不是开发用的 `npm run db:migrate`。
- CORS 当前允许 `*`，如果未来有 Web 前端，需要改为明确的允许域名。
- `OPENAI_MODEL` 当前文档和 env 示例使用 `gpt-5.5`，正式部署前需要确认托管环境和 OpenAI 账号可用模型。
- 如果 `BP_RECOGNITION_MODE=openai`，必须配置 `OPENAI_API_KEY`，否则服务启动会失败。
- iOS 端 staging URL 目前硬编码在 `APIClient.swift`，后续最好改为 build configuration 或环境配置。
- `.idea/`、`.codex-xcode-home/`、Xcode `xcuserdata/` 属于本地文件，不应该进入迁移或提交范围。
- `TodayAction` 目前是 iOS demo 和本地状态，不具备后端持久化能力，不能直接作为 Web Service 功能迁移。

  - `DATABASE_URL`
  - `ACCESS_TOKEN_SECRET`

  - `BP_RECOGNITION_MODE`

  - `OPENAI_MODEL`
  - `OPENAI_PROXY_URL`，如部署环境需要代理才配置。

  - `npm install`
